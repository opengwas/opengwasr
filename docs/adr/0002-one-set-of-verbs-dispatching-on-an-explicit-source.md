# One set of verbs, dispatching on an explicit Source

Every query function takes a Source (the API Source or a Local Source) and returns the same schema whichever it is given, so TwoSampleMR and other callers never branch on where data comes from. Backend parity is a tested contract. The user picks the Source explicitly: opengwasr never routes a query to a different Source on its own, and when the API refuses a query as too large (`413 request_too_large`) the error says how to download the Store instead. The API Source is pure R with no Python dependency, so installing opengwasr is enough to use it.

Behind the verbs, an API query is a Job: opengwasr submits it, polls at the server's `poll_after_seconds`/`Retry-After` with a capped backoff and overall timeout, and returns the rows, so the default experience is a plain blocking call. Submit, status, result and cancel are also exported for callers that fan out many Jobs. If the user interrupts the wait, the Job is left running and its id printed; resubmitting the same query reattaches to it, because the API deduplicates identical queries.

A Local Source is a directory holding one or more Store Releases. Analyses are named exactly as with the API Source, the latest Release of a Store is used unless one is pinned, and ambiguity is an error. opengwasr does not download Stores until an upstream distribution channel exists.

**Considered:** separate `api_*()`/`local_*()` families (rejected: every caller would duplicate its logic per backend); automatic routing by query size (rejected: hides cost and makes results depend on the environment).

**Clarification, 22 November 2026 (errors).** opengwasr behaves like every other OpenGWAS client: an error the API gives reaches the user as a condition whose message is the API's own (with the key redacted) and whose class comes from the API's error code, `opengwasr_<code>` (`opengwasr_analysis_not_found`, `opengwasr_request_too_large`, ...), under `opengwasr_refusal` for refusals, `opengwasr_busy` for the 429/503 family, and always `opengwasr_error`. Every code the API sends gets its class, listed or not; only an answer with no code is `opengwasr_api_error`. The API's code, status, message and body, and every other field of the body, stay on the condition. opengwasr checks something itself only where the API can't speak: no key set, R argument types and shapes, original units, Store Release ambiguity when `releases` is omitted, resolving a bare GWAS Store id, `ignored_fields`, Job-protocol invariants, and the limits it needs to split a request into Jobs. It never re-checks, or rewords, a refusal the API makes itself. Where opengwasr raises an error from an API answer that isn't an error (the Analysis lookup lists ids it can't resolve), the class and `api_error` are still the API's codes. The one table of codes and their parent classes is in `R/http.R`.

**Clarification, 25 November 2026 (a Local Source is the Store Releases it is given).** `og_local(path)` takes the full path of each Store Release, one per element, instead of a directory to scan. A Local Source holds at most one Release per GWAS Store, and two Releases of the same GWAS Store are refused when it is created. So no query chooses between Releases, and the "latest Release unless one is pinned" rule above doesn't arise locally. The API Source's rule is unchanged: with no recency field from the API, it refuses a GWAS Store that serves several Releases when none is pinned. `releases =` on a verb works on both Sources as a GWAS Store id or a `<store_id>/<release_id>` pin, and a Store Release the Source doesn't hold is refused (opengwas/opengwasr#2).

The layout rule, for any download channel to follow: **a GWAS Store directory holds one Store Release**, one level down (opengwas/opengwasr#38). So `og_local()` also takes a GWAS Store directory, such as `/data/opengwas/OGS-00011`: a path holding `manifest.json` is a Store Release directory, and one that doesn't is a GWAS Store directory, searched one level down and never deeper, so the Dense Component inside a Hybrid Store Release (`<release>/dense/manifest.json`) is never taken for a Store Release; a directory that looks like a Store Release (it holds `data.zarr` or `analyses.tsv`) but has lost its `manifest.json` is refused as no Store Release, never searched. Hidden directories, such as a build in progress, are skipped. One Store Release there is used. None is refused as no Store Release (`opengwasr_not_store_release`). Several are refused (`opengwasr_several_releases`), listing each by `<store_id>/<release_id>` and path, so the user passes the one they want; opengwasr never chooses between them. Other directories beside the Store Release (`replaced/`, `work/`, `tmp/` on opengwasdb's hosts) are ignored, since none holds a `manifest.json` of its own.
