# The Local Source reads through a standalone Store Reader

Local queries do not re-implement the store format in R and do not load the whole opengwasdb build package. Instead the read path of opengwasdb is split out into a standalone, read-only Store Reader with minimal dependencies (no pysam), defined by the store format spec plus golden fixture results, under GPL-3.0-only like all OpenGWAS software. The opengwasdb builder, ogdb-api, opengwasr and later the website all read through it, so there is one reader and API and local results agree by construction. ogld's LD Store reader follows the same pattern as a separate library.

The Store Reader is its own slim Python package (numpy, zarr and numcodecs only), so that the opengwasdb builder and ogdb-api can depend on it directly without depending on a client package. Users never install it by name. opengwaspy depends on it and exposes it as opengwaspy's own Local Source (an optional extra), making opengwaspy the one Python client for both the API and local Store Releases. opengwasr's Local Source calls opengwaspy through reticulate. opengwasr's API Source stays pure R and does not go through opengwaspy, so two clients of the same API, one in R and one in Python, are kept in step by the API contract and their live tests. The reader does not need pysam: the query-path uses of tabix and BGZF (range queries, long-allele ALIDs, per-row variant records) move to `.npy` sidecars in a minor store-format version, and existing Store Releases are backfilled.

opengwasr stays one R package, pure R, with reticulate in `Suggests`: the API Source needs nothing beyond R, and the Local Source loads reticulate and the Store Reader only when it is first used. A time-boxed spike measures Rust (`zarrs`) against the scattered-lookup benchmarks, which are the MR access pattern and currently take about 1 s for 100 variants × 10 Analyses on OGS-00009. It also checks whether a chunk-shape change gets the same gain. If Rust is substantially faster (about 5× or more), the reader is ported, and the Python package keeps its API as a pyo3 wrapper. The Rust ships inside the Store Reader's prebuilt Python wheels, so opengwasr still calls it through reticulate and no R user ever compiles anything. Python is found either automatically (`py_require()` with uv, for laptops) or from an environment the user provides (`RETICULATE_PYTHON` or conda, for HPC); the user's choice wins. The Source abstraction in ADR 0002 means that switch does not change opengwasr's interface.

**Considered:** putting the reader code inside opengwaspy itself (the engine and server would depend on the client); routing opengwasr's API calls through opengwaspy too (every TwoSampleMR user would then need Python); reading the existing tabix files with a pure-Python BGZF/tabix reader (no format change, but parsing code in the reader and slower range queries); reticulate into the full opengwasdb package (heavy dependencies, Linux-only through pysam); a native R reader (a second implementation of the codecs, CSR, Hybrid merge and variant lookup, which could drift silently); committing to Rust immediately (unmeasured benefit, larger detour from the TwoSampleMR goal).

**Upstream:** the split itself is an opengwasdb decision and needs its own ADR and issue there.
